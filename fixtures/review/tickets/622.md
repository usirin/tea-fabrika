## In plain words

tea's CI check is meant to stop a pull request that breaks the published API without a changeset. Today it only looks at the import paths the package still has, so a pull request that deletes a whole import path (say `@demlik/tea/paginate`) passes with no changeset at all. That is the biggest break the policy covers, and it hurts anyone who imports that path and gets no warning in the changelog. We would make the check also look at the import paths the base commit had, and treat each one that is gone as a removal.

## What is wrong

`pnpm --filter @demlik/tea run api:ratchet` passes on a pull request that removes an export subpath and carries no changeset. `packages/tea/MAINTAINING.md` ("Removal, while 0.x") and ADR 0016 say that removal owes a `minor` changeset with a breaking-change note on a `stable` or `battery` subpath.

## Where it is in the code

- `packages/tea/src/api-ratchet/api-map.ts`: `readApiMap()` builds the map from the working tree's `package.json` `exports` only. A subpath the pull request deleted has no row.
- `packages/tea/src/api-ratchet/ratchet.ts`: `runApiRatchet()` hands that one map to `diffPublishedApi`.
- `packages/code-graph/src/api/diff.ts`: `diffPublishedApi()` reads both sides through the one map and loops only over its subpaths. `subpathsAtBase()` handles a subpath the base lacks (every name `added`). Nothing handles a subpath only the base has.
- `packages/code-graph/src/api/map.ts`: `checkedSubpath()` refuses a map entry whose source file is missing from the working tree, so tea cannot keep the deleted subpath in today's map either.
- `packages/code-graph/SPEC.md` §13.4 states the same one-map rule: the view runs on the base tree "with the same map".
