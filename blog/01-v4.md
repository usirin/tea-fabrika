# Fabrika was v3. This is v4.

On October 4, 2026, a little before noon, I sent an agent this:

> i want us to do a brainstorming session about, how we can actually rewrite the operator agent from kamp-us/phoenix's fabrika, and i wanna see if we actually inverse how we build & use that

By about 2 a.m. the next night the new repo had 58 commits and a log of 37
experiments. This post is about the first hour of that: why I started over on
something that already works, what "inverse" meant, and the small first step
that made the rest possible. The experiments get their own posts.

## Fabrika, my v3

Fabrika is the pipeline that runs our work in
[kamp-us/phoenix](https://github.com/kamp-us/phoenix) and
[kamp-us/demlik](https://github.com/kamp-us/demlik). An issue goes through six
steps: report, triage, plan, build, review, ship. Each step is a skill (a
markdown file that teaches Claude Code how to do one job) and an agent that
loads it. Today that's 29 skills and 8 agents. Beside them sits the `fabrika`
CLI, which does the exact checks: is this issue claimed, did CI pass, is this
PR mergeable.

Holding it all together is the operator. Its job is to carry one issue from
start to finish: spawn a builder, wait, read what came back, spawn a reviewer,
read that, spawn a shipper, and stop to ask a person when a step needs one.

The operator is a markdown file. Its skill, `operate`, opens like this:

> **The ledger is the only state** ... folded fresh by a verb on every read;
> you hold none, and a remembered state is a stale one.

That's good prose, and it's also a program. The skill file and its contract
are each well over 2,000 lines today. When the agent read it in that first
hour, it put it in a way I keep coming back to: most of it "teaches an LLM to
be a loop around a ledger the CLI already folds." The prose is the program, and
the model is the CPU.

Fabrika is my third try at agentic automation. I call it v3, and it works. It
builds, reviews and ships real changes. But three things about it kept
bothering me.

**It's hard to see into.** When a lane does something odd, the answer is in an
agent's context window, which is gone by the time I look.

**It's hard to test.** The routing lives in prose that an agent applies. You
can't unit test a paragraph. You run it on a real issue, with real tokens, and
watch.

**It gets things wrong in ways a prompt can't fix.** Two lines from fabrika's
own source say it better than I can. One is from the review code:

> one adjudicated-clean PR drew three FAILs in a row on a single criterion of
> that shape, at temperature 0.0 over byte-identical input.

The other is from the review skill's contract, explaining why fabrika does not
trust a local test run:

> a local re-run has returned another checkout's cached green three times in
> one session.

The same model, the same bytes, three different answers. A green test run that
belonged to some other folder. Each one got a fix, in more rules or another CLI
check. But every new rule written in prose is one more thing the next agent has
to read and apply by hand.

And there's a quieter cost. Phoenix has a `fabrika-pi` package, which is the
skills shipped again for another agent harness. Prose has to be ported to each
place it runs. Code is written once.

## The itch

The agent asked me early on what the itch was. Was it that the operator gets
things wrong, that it's slow and expensive, or that I can't see what it's
doing? My answer:

> combination of a little bit of both + an urge/itch to scratch to experiment on more deterministic workflows

The idea I had was to turn it around. Today the prose drives the loop and calls
the CLI. What if a program drove the loop and called the model? In my first
message I wrote that I wanted "fabrika as a big tea machine", where "every
skill and cli is actually part of a big living organism controlled
programmatically."

Later that afternoon, deep in an experiment about something else, I said the
same thing more plainly:

> i mean using jev is an idea, my real thing is making the operator & fabrika pipeline code driven, not harness driven.

That line is the whole project. Jev, the small classifier you'll meet in the
next post, was one tool we wanted to try. The goal was to move the loop out of
the harness (Claude Code, reading prose) and into code.

## What tea is

`@demlik/tea` is a library I maintain in
[demlik](https://github.com/kamp-us/demlik/tree/main/packages/tea). It's the
Elm Architecture in TypeScript. If you haven't met it, the whole idea fits in a
few lines:

- A **Model** is the state, as plain JSON.
- A **Msg** is something that happened.
- `update` takes the Model and a Msg and returns a new Model plus a list of
  commands. It's a pure function. It never calls the network or touches a file.
- A **Cmd** is a request for work, written as data: "run the tests", "ask the
  builder". The runtime does the work and feeds the result back in as a Msg.

So the machine never does anything. It only decides. Everything that touches
the world happens outside `update`, and comes back as a message.

That gives you a few things for free, and they're exactly what fabrika's
operator was missing. You can test `update` with no model and no network,
because it's a function. You can replay a list of messages and get the same
state back. And you can kill it. tea's docs say it like this: the runtime
"saves the new Model before it runs that transition's effects", and on boot it
re-issues whatever the Model was still waiting on. "The reducer never learns it
was interrupted."

The picture I use is a board game. The machine is the rulebook and the score
sheet. The agents are players. A player can be as clever as they like on their
turn, but they don't decide whose turn is next, and they don't keep the score.

Here is the first `update` we wrote, from the first commit, trimmed:

```ts
/** Ask the builder for a change. `feedback` is why the last attempt was sent back. */
export const build = Cmd.define("build", {
  input: z.object({ issue: Issue, feedback: z.string().nullable() }),
  ok: z.object({ summary: z.string() }),
  err: ["agent_failed"],
});

/** Run the tests and read the diff. No model is involved in this one. */
export const check = Cmd.define("check", {
  input: z.object({}),
  ok: z.object({ passed: z.boolean(), output: z.string(), diff: z.string() }),
  err: ["could_not_run"],
});

update: {
  start: (s, m) =>
    s.phase === "idle"
      ? [{ phase: "building", issue: m.issue, attempt: 1, feedback: null },
         [build({ issue: m.issue, feedback: null })]]
      : stay(s),
  build_ok: (s) =>
    s.phase === "building"
      ? [{ phase: "checking", issue: s.issue, attempt: s.attempt }, [check({})]]
      : stay(s),
  // ...
}
```

`build` is the only place a model writes anything. `check` runs the tests and
reads the diff with no model at all. And "how many tries are left" is a number
in the Model, not something an agent remembers.

One caveat from tea's own docs matters here: effects run at least once. If the
process dies after the builder started but before its answer was saved, the
builder runs again. For an agent that writes files, that's a real question, and
the agent raised it the moment we planned kill and resume: a rerun build starts
on a half-changed folder.
