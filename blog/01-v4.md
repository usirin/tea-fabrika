# Fabrika was v3. This is v4.

58 commits and 37 experiments. That's what a new repo had by about 2 a.m. on
October 5, 2026, starting from a brainstorm a little before noon the day
before. The brainstorm had one question in it. Could I take the operator out of
fabrika, my agent pipeline, and turn the whole thing inside out?

This post is about the first few hours: why I started over on something that
already works, what "inside out" meant, and the small first step that made the
rest possible. The experiments get their own posts.

## Fabrika, my v3

Fabrika is the pipeline that runs our work in
[kamp-us/phoenix](https://github.com/kamp-us/phoenix) and
[kamp-us/demlik](https://github.com/kamp-us/demlik). An issue goes through six
steps: report, triage, plan, build, review, ship. Each step is a skill (a
markdown file that teaches Claude Code how to do one job) and an agent that
loads it. Today that's 29 skills and 8 agents. Next to them sits the `fabrika`
CLI, which does the exact checks. Is this issue claimed? Did CI pass? Is this
PR mergeable?

The operator holds it all together. Its job is to carry one issue from start to
finish. It spawns a builder, waits, reads what came back, spawns a reviewer,
reads that, spawns a shipper, and stops to ask a person when a step needs one.

The operator is a markdown file. Its skill, `operate`, opens by telling the
agent that the ledger is the only state, that it holds none of it, and that "a
remembered state is a stale one". That's good writing. It's also a program. The
skill file and its contract are each about 2,500 lines. When the agent read
them in that first hour, its summary was that most of those lines teach a model
to be a loop around a ledger the CLI already reads. The prose is the program,
and the model is the CPU.

Fabrika is my third try at agentic automation, so I call it v3. It works. It
builds, reviews and ships real changes. But three things about it kept
bothering me.

**It's hard to see into.** The ledger says what a lane did. When a lane does
something odd, the reason sits in an agent's context window, and that's gone by
the time I look.

**It's hard to test.** The routing lives in prose that an agent applies. You
can't unit test a paragraph. You run it on a real issue, spend real tokens, and
watch.

**It gets things wrong in ways a prompt can't fix.** Fabrika's own source keeps
a record of these. A comment in the review code describes one clean PR that got
three FAILs in a row on the same criterion, "at temperature 0.0 over
byte-identical input". The review skill explains why fabrika stopped trusting
local test runs: one had handed back "another checkout's cached green" three
times in one session. The same wrong answer three times, on bytes that should
have passed. A green run that belonged to a different folder. Each one got a
fix, as one more rule or one more CLI check. But every rule written in prose is
another thing the next agent has to read and apply by hand.

There's a quieter cost too. Phoenix has a `fabrika-pi` package, which bundles
every skill and agent again for a different agent harness, pi. Prose only runs
where something reads it, so each new harness needs its own copy. A program
just runs.

## The itch

Early on the agent asked me what was really bugging me. Was it the mistakes,
the cost, or not being able to see inside? Honestly, a bit of all three. But
mostly I wanted to experiment. I'd been curious for a while about workflows
that are more deterministic, and this was my excuse.

The idea was to flip the direction. Today the prose drives the loop and calls
the CLI. What if a program drove the loop and called the model? I pictured
fabrika as one big tea machine, where every skill and every CLI verb is a part
of one system that code controls.

A few hours later, in the middle of an experiment about something else, I said
it again, more plainly. Jev, the small model you'll meet in the next post, was one tool we
wanted to try. It was never the point. The point was to make the operator and
the pipeline code driven instead of harness driven: move the loop out of Claude
Code reading prose, and into code.

That's the whole project in one sentence.

## What tea is

`@demlik/tea` is my brother's library. It lives in
[demlik](https://github.com/kamp-us/demlik/tree/main/packages/tea), and
everything in this series is built on top of it. It's the Elm Architecture in
TypeScript. If you haven't met it, the whole idea fits in a few lines:

- A **Model** is the state, as plain JSON.
- A **Msg** is something that happened.
- `update` takes the Model and a Msg and returns a new Model plus a list of
  commands. It's a pure function. It never calls the network or touches a file.
- A **Cmd** is a request for work, written as data: run the tests, ask the
  builder. The runtime does the work and feeds the result back in as a Msg.

So the machine never does anything. It only decides. Everything that touches
the world happens outside `update` and comes back as a message.

That gives you a few things for free, and they're the things fabrika's operator
was missing. You can test `update` with no model and no network, because it's a
function. You can replay a list of messages and get the same state back. And
you can kill it. tea's docs explain that the runtime "saves the new Model before
it runs that transition's effects", and on boot it sends again whatever the
Model was still waiting on. "The reducer never learns it was interrupted."

I think of it as a board game. The machine is the rulebook and the score sheet.
The agents are players. A player can be as clever as they like on their turn,
but they don't decide whose turn is next, and they don't keep the score.

Here's the first `update` we wrote, from the first commit, trimmed:

```ts
/** Ask the builder for a change. `feedback` is why the last attempt was sent back. */
export const build = Cmd.define("build", {
  input: z.object({ issue: Issue, feedback: z.string().nullable() }),
  ok: z.object({ summary: z.string() }),
  err: ["agent_failed"],
});

/** Run the tests and read the diff. No model is involved in this one. */
export const check = Cmd.define("check", {
  input: z.object({}),
  ok: z.object({ passed: z.boolean(), output: z.string(), diff: z.string() }),
  err: ["could_not_run"],
});

update: {
  start: (s, m) =>
    s.phase === "idle"
      ? [{ phase: "building", issue: m.issue, attempt: 1, feedback: null },
         [build({ issue: m.issue, feedback: null })]]
      : stay(s),
  build_ok: (s) =>
    s.phase === "building"
      ? [{ phase: "checking", issue: s.issue, attempt: s.attempt }, [check({})]]
      : stay(s),
  // ...
}
```

`build` is the only place a model writes anything. `check` runs the tests and
reads the diff with no model at all. And how many tries are left is a number in
the Model, not something an agent has to remember.

One warning from tea's docs matters here. Effects run at least once. If the
process dies after the builder started but before its answer was saved, the
builder runs again. For an agent that writes files, that's a real problem, and
the agent pointed it out as soon as we planned kill and resume: a second build
starts on a half-changed folder.

## Start smaller than you want to

The brainstorm got big fast. Epics as parent machines, the builder on one model
and the reviewer on another, parks you answer from a chat window. I pulled it
back. I wanted everything else set aside until we had a minimal repro. The agent
cut the idea down to one lane on a toy repo, and I made a repo for it.

Then, right before it started writing code, I stopped it. I wasn't sure it had
a plan or was just going on feel. So I asked. It admitted it was about half and
half: it had a plan in its head, and parts of it were unchecked. So it wrote the
plan down.

1. A lane machine and a fake agent, tests only. This settles the shape.
2. Real test runs in a toy repo, with the state saved to disk. Kill it mid-run
   and it resumes.
3. A real Jev call as the judge.
4. A real backend, Claude Code run headless, as the builder.

And a finish line: one command takes a toy issue with a failing test to green
and judged, with a log you can replay.

No GitHub, no pull requests, no CI, no epics. Fabrika runs on a real repo with
real issues. The repro would run on toys in a temp folder. That leaves out the
messy parts where the prose operator earns its keep, and we said so up front.
The point was to see the shape before paying for the mess.

The toys ended up as two small functions. `slugify` turns a title into a URL
slug, with three rules. `parseDuration` turns `"1h30m"` into seconds, with six.
Each toy has one correct version and several broken on purpose, each breaking
one rule. That's what gives every experiment a known answer: run the real tests
and see.

The first commit, `6e9a510`, landed at 12:24, 28 minutes after the brainstorm
started. It had the lane machine, a scripted builder, a scripted workspace, a
scripted judge, and 8 tests. Every service had a fake, so the whole lane ran
start to finish with no model and no network. It typechecked against the
published tea 0.19.0 on the first try. (tea 0.20.0 came out while all this was
going on. The repo stayed on 0.19.0.)

After that the slices came fast, because the shape was settled. A runnable demo
with real test runs and a real Jev judge at 12:49. Claude Code as the builder,
one conversation per lane, at 13:02. A triage machine that hands its issue to
the lane at 13:22.

I want to stay on that first commit for a second, because I think it's the most
useful thing in this post. Before any model was involved, one test drove a whole
lane from start to done, and another drove it around the retry loop until it
ran out of tries. When the real builder showed up less than an hour later, it
slotted in behind a contract the tests had already pinned down. Nothing about
the loop had to change to make room for it.

## The first real answer

Step three of the plan, a real Jev call, gave us the first surprise within an
hour.

Jev is a small classifier from TypeSafe. You give it some text and a
multiple-choice question, and it gives back one answer and a confidence between
0 and 1. The lane asked it, for each rule on the ticket, whether the change met
the rule, and only acted on answers at or above a floor of 0.8.

Its first real answer was "met", at 0.81. Then the agent ran the same demo four
times. It finished once and parked three times. One rule, "drop odd
characters", kept coming back "met" at around 0.68, under the floor. The lane
did what we told it to do. It stopped and asked for a person.

I'd been poking at the same rule myself, asking Jev the same question again and
again. I got 0.69, 0.79, 0.64 and 0.77. It looked like noise.

It wasn't. The rule said anything outside a-z and 0-9 gets dropped, but a slug
keeps its dashes. The rule contradicted the code, and Jev was telling us so the
only way it can, by being unsure. With the rule reworded, the demo finished six
runs out of six.

That turned into a whole line of experiments, and the next post is about them.
For this one, what matters is where the lesson pointed. An unsure judge didn't
mean a person should look at the code. It meant the ticket was badly written,
and that's triage's job. The machine made that visible because "unsure" was a
state with a name, not a feeling inside an agent's context.

## Three owners

By the end of the first afternoon the idea had settled into three rules. They
sit at the top of the repo's README, and everything since hangs off them.

**The machine owns the loop and the facts.** Which step are we on, did the tests
pass, how many tries are left. No agent is asked any of those, and no agent is
trusted to remember them.

**Agents own the writing.** Rewriting a rough ticket, writing code. Each one
sits behind a small service, so Claude Code can be swapped for another agent,
or for a script in the tests. And each one ends its turn in a typed answer, so
code can route on a field instead of reading prose. Here's the builder's answer
as it is today:

```ts
/**
 * How a build ended, in the builder's own words. `done` lists the files it
 * changed beyond the ticket. `contradiction` names an example that breaks its
 * own rule, which the builder must not code to; `blocked` is work it cannot do
 * from here; `dispute` names a review finding it thinks is wrong. None is a
 * failure: each goes to a person with the builder's reason.
 */
export type BuildAnswer =
  | { readonly kind: "done"; readonly summary: string; readonly deviations: readonly Deviation[] }
  | { readonly kind: "contradiction"; readonly criterion: string; readonly call: string; readonly why: string }
  | { readonly kind: "blocked"; readonly why: string }
  | { readonly kind: "dispute"; readonly finding: string; readonly why: string };
```

Fabrika already has a version of this. Each shell ends its run on a final
token, and the CLI maps it in code. The difference here is that the answer
carries its fields (which example, which rule, why), and the machine routes on
them with no agent reading in between. The builder can't answer anything else.
A contradiction isn't a failure either. It's the builder raising its hand: this
example breaks its own rule, so I won't code to it. Code parks the lane and
shows a person the rule and the example side by side.

**Jev owns narrow yes/no calls.** A small, cheap classifier answers one
multiple-choice question with a confidence, and the machine acts only above a
floor. Below it, the answer is "unsure", and unsure has somewhere to go.

I got one thing wrong in that first design, and I'll say it now because the
series keeps coming back to it. The first lane asked Jev whether the diff met
each rule. A model reading a diff and deciding "done". By experiment 24 that was
gone. Triage writes each rule with an example call and its exact result, code
turns those into tests, and the tests decide. The experiment log puts it
plainly: "No person or model judged anything after triage." Posts 3 to 5 are
how we got there.

## Every step a state

Over the next twelve hours the lane grew into four machines. Triage turns a
rough ticket into rules with examples, and sorts it. The lane writes the tests,
builds, runs them, and retries. Review is a child machine the lane holds while
it reviews. Ship seals the change as one commit and waits for a person to
approve that exact commit before it lands. A factory machine holds all of them
and hands work from one to the next.

What they share is that every stop is a state with a name. When a lane needs a
person, it parks, and a park is one of a closed list of causes:
`contradiction`, `finding_disputed`, `out_of_attempts`, `comment_changes_rule`,
and a few more. Each cause takes one kind of typed answer. An answer that
doesn't fit the park the lane is in leaves it parked.

The kill test happened for real, with real agents. In experiment 23 a real
build got a SIGINT five seconds after Claude Code started, and the same command
ran again. The saved state said `building`, with the builder's conversation id
already in it. The lane sent the build again into the same Claude conversation.
Claude's own log of that conversation holds both turns, eight seconds apart. No
agent had to remember where it was, because the machine knew.

Halfway through, two agents read every fabrika skill and wrote down who should
own each decision once it's a machine. The [skill map](../docs/skill-map.md)
has the details, but one finding surprised me. Most of fabrika is already code.
The CLI verbs make the exact checks, and the agent mostly reads an exit code
and looks up what to do next in a table the skill spells out in prose. The
skills even call that table "a total function of the code". In tea, that table
is the reducer. Turning fabrika inside out wasn't about adding code. It was
about moving code that already existed out of a paragraph and into a function.

## What I'd tell you to steal

If you run agents on real work, here's what I'd take from these first hours,
whether or not you ever touch tea.

**Put the loop in code.** If your agent's instructions read like "on exit code
X, do Y", that's a function someone is running by hand. Write the function.
Keep the model for the open-ended parts.

**End every agent turn in a typed answer.** Not a paragraph that says it's done,
but one of a few named values, each with its fields. Code routes on the field.
If the agent can't fit its answer into one of them, you just found a value you
needed and didn't have.

**Make every stop a named state.** A park is a closed list of causes, and each
cause takes one kind of answer. Then "why is this stuck?" is a lookup, not an
investigation.

**Build the fake first.** Put every agent and every outside service behind a
small contract, and write a scripted version of each before the real one. Our
whole lane ran in a test with no model 28 minutes in, and that's why the real
agents were easy to add after it.

**Save the state before the side effect, then kill it on purpose.** If you
can't kill your pipeline mid-step and start it again, you don't know where its
state lives. Ours lives in one `state.json` you can print.

## v3 to v4

Around 1 a.m., a few minutes after a config file took the knobs out of the
code, I noticed I was really excited about where this was going. Fabrika was v3
of my agentic automation experiments, and this one would become v4.

Here's the difference as I see it. v3 is a pipeline that lives inside an agent
harness, written as prose. v4 is a set of systems with SDKs: machines,
services, a classifier, a tracker, a repo. You compose them in code, test them
like code, and swap any one of them out. Claude Code is still in there. It
writes the code. It just doesn't run the loop anymore.

The lane hasn't run on a real issue yet. It's a repro on two toy tickets, with a
list of things not built at the bottom of the README, and I'm not sure yet how
much of it survives a real repo. But I know where the state lives, I can kill
it, and when it stops it tells me why in a word I can look up.
