# Fabrika was v3. This is v4.

On October 4, 2026, a little before noon, I sent an agent this:

> i want us to do a brainstorming session about, how we can actually rewrite the operator agent from kamp-us/phoenix's fabrika, and i wanna see if we actually inverse how we build & use that

By about 2 a.m. that night the new repo had 58 commits and a log of 37
experiments. This post is about the first hour of that: why I started over on
something that already works, what "inverse" meant, and the small first step
that made the rest possible. The experiments get their own posts.

## Fabrika, my v3

Fabrika is the pipeline that runs our work in
[kamp-us/phoenix](https://github.com/kamp-us/phoenix) and
[kamp-us/demlik](https://github.com/kamp-us/demlik). An issue goes through six
steps: report, triage, plan, build, review, ship. Each step is a skill (a
markdown file that teaches Claude Code how to do one job) and an agent that
loads it. Today that's 29 skills and 8 agents. Beside them sits the `fabrika`
CLI, which does the exact checks: is this issue claimed, did CI pass, is this
PR mergeable.

Holding it all together is the operator. Its job is to carry one issue from
start to finish: spawn a builder, wait, read what came back, spawn a reviewer,
read that, spawn a shipper, and stop to ask a person when a step needs one.

The operator is a markdown file. Its skill, `operate`, opens like this:

> **The ledger is the only state** ... folded fresh by a verb on every read;
> you hold none, and a remembered state is a stale one.

That's good prose, and it's also a program. The skill file and its contract
are each well over 2,000 lines today. When the agent read it in that first
hour, it put it in a way I keep coming back to: most of it "teaches an LLM to
be a loop around a ledger the CLI already folds." The prose is the program, and
the model is the CPU.

Fabrika is my third try at agentic automation. I call it v3, and it works. It
builds, reviews and ships real changes. But three things about it kept
bothering me.

**It's hard to see into.** When a lane does something odd, the answer is in an
agent's context window, which is gone by the time I look.

**It's hard to test.** The routing lives in prose that an agent applies. You
can't unit test a paragraph. You run it on a real issue, with real tokens, and
watch.

**It gets things wrong in ways a prompt can't fix.** Two lines from fabrika's
own source say it better than I can. One is from the review code:

> one adjudicated-clean PR drew three FAILs in a row on a single criterion of
> that shape, at temperature 0.0 over byte-identical input.

The other is from the review skill's contract, explaining why fabrika does not
trust a local test run:

> a local re-run has returned another checkout's cached green three times in
> one session.

The same wrong answer three times, on bytes that should have passed. A green
test run that belonged to some other folder. Each one got a fix, in more rules or another CLI
check. But every new rule written in prose is one more thing the next agent has
to read and apply by hand.

And there's a quieter cost. Phoenix has a `fabrika-pi` package, which is the
skills shipped again for another agent harness. Prose has to be ported to each
place it runs. Code is written once.

## The itch

The agent asked me early on what the itch was. Was it that the operator gets
things wrong, that it's slow and expensive, or that I can't see what it's
doing? My answer:

> combination of a little bit of both + an urge/itch to scratch to experiment on more deterministic workflows

The idea I had was to turn it around. Today the prose drives the loop and calls
the CLI. What if a program drove the loop and called the model? In my first
message I wrote that I wanted "fabrika as a big tea machine", where "every
skill and cli is actually part of a big living organism controlled
programmatically."

Later that afternoon, deep in an experiment about something else, I said the
same thing more plainly:

> i mean using jev is an idea, my real thing is making the operator & fabrika pipeline code driven, not harness driven.

That line is the whole project. Jev, the small classifier you'll meet in the
next post, was one tool we wanted to try. The goal was to move the loop out of
the harness (Claude Code, reading prose) and into code.

## What tea is

`@demlik/tea` is a library I maintain in
[demlik](https://github.com/kamp-us/demlik/tree/main/packages/tea). It's the
Elm Architecture in TypeScript. If you haven't met it, the whole idea fits in a
few lines:

- A **Model** is the state, as plain JSON.
- A **Msg** is something that happened.
- `update` takes the Model and a Msg and returns a new Model plus a list of
  commands. It's a pure function. It never calls the network or touches a file.
- A **Cmd** is a request for work, written as data: "run the tests", "ask the
  builder". The runtime does the work and feeds the result back in as a Msg.

So the machine never does anything. It only decides. Everything that touches
the world happens outside `update`, and comes back as a message.

That gives you a few things for free, and they're exactly what fabrika's
operator was missing. You can test `update` with no model and no network,
because it's a function. You can replay a list of messages and get the same
state back. And you can kill it. tea's docs say it like this: the runtime
"saves the new Model before it runs that transition's effects", and on boot it
re-issues whatever the Model was still waiting on. "The reducer never learns it
was interrupted."

The picture I use is a board game. The machine is the rulebook and the score
sheet. The agents are players. A player can be as clever as they like on their
turn, but they don't decide whose turn is next, and they don't keep the score.

Here is the first `update` we wrote, from the first commit, trimmed:

```ts
/** Ask the builder for a change. `feedback` is why the last attempt was sent back. */
export const build = Cmd.define("build", {
  input: z.object({ issue: Issue, feedback: z.string().nullable() }),
  ok: z.object({ summary: z.string() }),
  err: ["agent_failed"],
});

/** Run the tests and read the diff. No model is involved in this one. */
export const check = Cmd.define("check", {
  input: z.object({}),
  ok: z.object({ passed: z.boolean(), output: z.string(), diff: z.string() }),
  err: ["could_not_run"],
});

update: {
  start: (s, m) =>
    s.phase === "idle"
      ? [{ phase: "building", issue: m.issue, attempt: 1, feedback: null },
         [build({ issue: m.issue, feedback: null })]]
      : stay(s),
  build_ok: (s) =>
    s.phase === "building"
      ? [{ phase: "checking", issue: s.issue, attempt: s.attempt }, [check({})]]
      : stay(s),
  // ...
}
```

`build` is the only place a model writes anything. `check` runs the tests and
reads the diff with no model at all. And "how many tries are left" is a number
in the Model, not something an agent remembers.

One caveat from tea's own docs matters here: effects run at least once. If the
process dies after the builder started but before its answer was saved, the
builder runs again. For an agent that writes files, that's a real question, and
the agent raised it the moment we planned kill and resume: a rerun build starts
on a half-changed folder.

## Start smaller than you want to

The agent's first answer was a big picture. Epics as parent machines, the
builder on one model and the reviewer on another, parks you answer from a chat
window. It was exciting, and it was a lot. So I asked:

> hmm, are we just going with vibes? or do you have a plan in your mind?

The answer started with "Honestly, half and half." It had a plan in its head
and hadn't checked parts of it. Then it wrote the plan down:

1. A lane machine and a fake agent, tests only. This settles the shape.
2. Real test runs in a toy repo, with the state saved to disk. Kill it mid-run
   and it resumes.
3. A real Jev call as the judge.
4. A real backend, Claude Code run headless, as the builder.

And a line for when it's done: one command takes a toy issue with a failing
test to green and judged, with a log you can replay.

No GitHub, no pull requests, no CI, no epics. Fabrika runs on a real repo with
real issues. The repro would run on toys in a temp folder. That leaves out the
messy parts where the prose operator earns its keep, and we said so up front.
The point was to see the shape before paying for the mess.

The toys ended up as two small functions. `slugify` turns a title into a URL
slug, with three rules. `parseDuration` turns `"1h30m"` into seconds, with six.
Each toy has one correct version and several broken on purpose, each breaking
one rule. That's what gives every experiment a known answer: run the real tests
and see.

The first commit, `6e9a510`, landed at 12:24, 28 minutes after my first
message. It was the lane machine, a scripted builder, a scripted workspace, a
scripted judge, and 8 tests. Every service had a fake, so the whole lane ran
start to finish with no model and no network. It typechecked against the
published tea 0.19.0 on the first try. (tea 0.20.0 came out while all this was
going on; the repo was built on 0.19.0.)

Then the slices came fast, because the shape was settled. A runnable demo with
real test runs and a real Jev judge at 12:49. Claude Code as the builder, one
conversation per lane, at 13:02. A triage machine that hands its issue to the
lane at 13:22.

I want to stay on that first commit for a second, because I think it's the
most stealable thing in this post. Before any model was involved, there was a
test that drove a whole lane from start to done, and another that drove it
around the retry loop until it ran out of tries. When the real builder showed
up an hour later, it slotted in behind a contract the tests had already pinned
down. Every bug after that was either in the machine, where a test could catch
it, or in the agent's work, where the machine could see it.

## The first real answer

The third step of the plan, a real Jev call, gave us the first surprise of the
project within an hour.

Jev is a small classifier from TypeSafe. You give it some text and a
multiple-choice question, and it gives back one answer and a confidence between
0 and 1. The lane asked it, for each rule on the ticket, whether the change met
the rule, and only acted on an answer at or above a floor of 0.8.

Its first real answer was "met", at 0.81. Then the agent ran the same demo four
times. It finished once and parked three times. One rule, "drop odd
characters", kept coming back "met" with a confidence around 0.68, under the
floor. The lane did exactly what we told it: it stopped and asked for a person.

I'd already been poking at that myself:

> yeah i literally did the same test to see how stable/steady jev is. my tests: 0.69, 0.79, 0.64, 0.77

It looked like noise. It wasn't. The rule said anything outside a-z and 0-9 gets
dropped, but a slug keeps its dashes. The rule contradicted the code, and Jev
was telling us so in the only way it can, by being unsure. Reworded, it
finished six runs out of six.

That turned into a whole line of experiments, and the next post is about them.
What matters for this one is where the lesson pointed. An unsure judge didn't
mean "a person should look at the code". It meant the ticket was badly written,
which is triage's job. The machine made that visible because "unsure" was a
state with a name, not a feeling in an agent's context.

## Three owners

By the end of the first afternoon the idea had settled into three rules. They
are the top of the repo's README, and everything since hangs off them.

**The machine owns the loop and the facts.** What step are we on, did the tests
pass, how many tries are left. No agent is asked any of those, and no agent is
trusted to remember them.

**Agents own the writing.** Rewriting a rough ticket, writing code. Each one
sits behind a small service, so Claude Code can be swapped for another agent,
or for a script in the tests. And each one ends its turn in a typed answer, so
code can route on a field instead of reading prose. Here is the builder's
answer, as it is today:

```ts
/**
 * How a build ended, in the builder's own words. `done` lists the files it
 * changed beyond the ticket. `contradiction` names an example that breaks its
 * own rule, which the builder must not code to; `blocked` is work it cannot do
 * from here; `dispute` names a review finding it thinks is wrong. None is a
 * failure: each goes to a person with the builder's reason.
 */
export type BuildAnswer =
  | { readonly kind: "done"; readonly summary: string; readonly deviations: readonly Deviation[] }
  | { readonly kind: "contradiction"; readonly criterion: string; readonly call: string; readonly why: string }
  | { readonly kind: "blocked"; readonly why: string }
  | { readonly kind: "dispute"; readonly finding: string; readonly why: string };
```

Compare that with fabrika today, where a shell prints a terminal token at the
end of its run and the operator skill spends a lot of words on not trusting it.
Here the builder can't answer anything else. A "contradiction" isn't a failure
either. It's the builder raising its hand: this example breaks its own rule, so
I won't code to it. Code parks the lane and shows a person the rule and the
example side by side.

**Jev owns narrow yes/no calls.** A small, cheap classifier answers one
multiple-choice question with a confidence, and the machine acts only above a
floor. Below it, the answer is "unsure", and unsure has somewhere to go.

I got one thing wrong in that first design, and it's worth saying now because
the series keeps coming back to it. The first lane asked Jev whether the diff
met each rule. A model reading a diff and deciding "done". By experiment 24 that
was gone: triage writes each rule with an example call and its exact result,
code turns those into tests, and the tests decide. As the experiment log puts
it, "No person or model judged anything after triage." Posts 3 to 5 are how we
got there.

## Every step a state

Over the next twelve hours the lane grew into four machines. Triage turns a
rough ticket into rules with examples, and sorts it. The lane writes the tests,
builds, runs them, and retries. Review is a child machine the lane holds while
it reviews. Ship seals the change as one commit and waits for a person to
approve that exact commit before it lands. A factory machine holds all of them
and hands work from one to the next.

The thing they share is that every stop is a state with a name. When a lane
needs a person, it parks, and a park is one of a closed list of causes:
`contradiction`, `finding_disputed`, `out_of_attempts`, `comment_changes_rule`,
and a few more. Each cause takes one kind of typed answer. An answer that
doesn't fit the park the lane is in leaves it parked.

And the kill test happened for real, with real agents. In experiment 23 a real
build got a SIGINT five seconds after Claude Code started, and the same command
was run again. The saved state said `building`, with the builder's conversation
id already in it. The lane sent the build again into the same Claude
conversation. Claude's own log of that conversation holds both turns, the killed
one at 03:41:57 and the new one at 03:42:05. No agent had to remember where it
was, because the machine knew.

Halfway through, two agents read every fabrika skill and wrote down who should
own each decision once it's a machine. The [skill map](../docs/skill-map.md)
has the details, but one finding surprised me. Most of fabrika is already code.
The CLI verbs make the exact checks, and the agent mostly reads an exit code and
looks up what to do next in a table the skill spells out in prose, a table the
skills themselves call "a total function of the code". In tea that table is the
reducer. The inversion wasn't about adding code. It was about moving the code
that was already there out of a paragraph and into a function.

## What I'd tell you to steal

If you run agents on real work, here's what I'd take from these first hours,
whether or not you ever touch tea.

**Put the loop in code.** If your agent's instructions read like "on exit code
X, do Y", that's a function someone is running by hand. Write the function.
Keep the model for the parts that are open-ended.

**End every agent turn in a typed answer.** Not a paragraph that says "done!",
but one of a few named values, each with its fields. Code routes on the field.
If the agent can't fit its answer into one of them, that's a new value you
needed and didn't have.

**Make every stop a named state.** A park is a closed list of causes, and each
cause takes one kind of answer. Then "why is this stuck?" is a lookup, not an
investigation.

**Build the fake first.** Put every agent and every outside service behind a
small contract, and write a scripted version of each before the real one. Our
whole lane ran in a test with no model before lunch, and that's why the real
agents were easy to add after it.

**Save the state before the side effect, then kill it on purpose.** If you
can't kill your pipeline mid-step and start it again, you don't know where its
state lives. Ours lives in one `state.json` you can print.

## v3 to v4

Around 1 a.m., a few minutes after a config file took the knobs out of the
code, I wrote this:

> i am feeling really excited about where we are going tbh. fabrika was my v3 of agentic automation experiments, and this one is gonna become the v4 -> systems that has sdks so you can compose them at code level instead of trying to do everything inside claude code.

That's still the best way I can say it. v3 is a pipeline that lives inside an
agent harness, written as prose. v4 is a set of systems with SDKs: machines,
services, a classifier, a tracker, a repo. You compose them in code, test them
like code, and swap any one of them out. Claude Code is still in there. It
writes the code. It just doesn't run the loop anymore.

None of this runs on real issues yet. It's a repro on two toy tickets, with a
list of things not built at the bottom of the README, and I'm not sure yet how
much of it survives a real repo. But I know where the state lives, I can kill
it, and when it stops it tells me why in a word I can look up.
