# 183: Can a running program take new code and keep its state?

**Yes, in the brain, in Miniflare, for `next/`.** A program's process swapped to new code
between two Msgs and kept its model, in 23 ms at the median (26 ms at p95). A new state shape
went through an upcast, Erlang's `code_change`. A shape the new code could not read was refused,
and that one process stayed on the old code. A module that threw as it loaded never ran. A step
that threw was rolled back and the same Msg ran once on the old code. Every step's entry names
the build that ran it. Two things must be designed in, and the test shows why:

- **The swap must go through the process's queue.** Sent around it, two Msgs that were already
  running finished on the old code after the swap, wrote the old shape over the new one, and the
  counter became `null` in 5 of 5 runs. Every entry in the log still looked fine.
- **Each save costs about 4 MB of workerd memory, and none came back.** 60 saves took workerd from
  171 MB to 421 MB, still 421 MB after 20 s idle. A restart on the same data folder kept the
  model and the running build, and answered in 56 ms. So the plan for memory is a planned
  restart, which loses nothing, not a hope that old isolates go away.

The owner decided on 2026-11-01 that `next/` has hot reload from day one. This experiment
measures one way to build it and reads how about ten tools do it. The proposal is
[hot reload](../docs/direction/hot-reload.md), and a private page, "Hot reload guidelines", lets
you press the six principles. Today's version (`apps/fabrika`) is not changed and was not run.
No model, no key, $0.

```ts
// The whole idea, in the brain (a sketch from this run's core.ts).
// An agent saves programs/counter/src/machine.ts. dev.ts bundles it, hashes it, and sends it.
{_tag: "code.loaded", body: {program: "counter", hash: "67896c9f...", was: "0b1e...", from: "watch"}}
// Each `counter` process takes it at its next step boundary, through its own mailbox:
//   new code decodes the model           -> keep the model, swap update and view
//   it decodes after the version's upcast -> keep the migrated model (Erlang's code_change)
//   it does not decode                    -> code.refused; this process stays on the old code
// And every step says which build ran it:
{_tag: "stepped", body: {id: "m5", build: "67896c9f..."}}
```

## How it was run

- Today's version is not touched. This is a lab model of `next/`'s brain, built on
  [experiment 173](./173-worker-loader.md)'s shape: a core Durable Object, `Process`, keeps the
  model, the running hash and a small log in its own storage. Each program version is a pure step
  behind Worker Loader, `LOADER.get(hash, ...)`, with `globalOutbound: null`.
- A version answers four calls: `init`, `migrate`, `step` and `view` (`183-hmr/define.ts`).
  `migrate` is the state check from [an old host is named, then restarted](../docs/direction/an-old-host-is-named-then-restarted.md):
  decode the saved model with this version's own Effect schema, after an optional upcast, or say
  why not.
- Five versions of one counter, as an agent might save them in a row (`183-hmr/versions.ts`).
  esbuild bundles each one on its own, 316 KB minified (Effect's Schema is most of it).
- Four parts: the swaps above; a race of 200 Msgs at once with a swap after the 100th, five runs
  through the queue and five around it; 60 saves in a row, each a new hash; and a new Miniflare
  on the same data folder.
- Miniflare 4.20260730.0 (workerd 1.20260730.1), esbuild 0.28.2, Effect 4.1.1, Node 26.13.0, on a
  laptop, under `nice -n 15`. Run twice; the numbers here are the second run, and the first agreed
  within 3 ms and 10 MB.

## The race: why the swap goes through the queue

A Durable Object takes the next call while a step awaits the isolate. So a swap that does not wait
its turn can land inside a step.

| Swap | Runs | Steps logged | Steps on old code | Steps on new code | Model at the end |
|---|---|---|---|---|---|
| through the queue | 5 | 200 of 200 | 100 | 100 | `{count: 200}`, right |
| around the queue | 5 | 200 of 200 | 98 | 102 | `{count: null}`, lost |

- Around the queue, two old-code steps were still running when the swap wrote `{count: 100}`.
  They finished and wrote `{n: 101}` and `{n: 102}` over it. The next new-code step read
  `m.count` from `{n: 102}` and got `NaN`, saved as `null`.
- Nothing threw. Every Msg has its `stepped` entry. Only a law on the model catches it: "after a
  reload, the model equals a run of every Msg in order, with each on the code it was logged with."
- This is Erlang's answer for the same reason. `sys:change_code` needs the process suspended
  first ("The process must be suspended to handle this message",
  [sys](https://www.erlang.org/doc/apps/stdlib/sys.html)), and the release handler "suspends, asks
  for code change, and resumes processes"
  ([release handling](https://www.erlang.org/doc/system/release_handling.html)). Our mailbox is
  the suspend: a swap is one more message in it.

## Memory: each save stays

| Saves | workerd memory |
|---|---|
| 0 | 171 MB |
| 10 | 235 MB |
| 30 | 309 MB |
| 60 | 421 MB |
| 60, then 20 s idle | 421 MB |

- About 4.2 MB a save, with the 316 KB Effect-bearing bundle. Experiment 173 measured about
  6.5 MB a version, and its part 2 measured 1.2 to 2.1 MB for a pure step with Effect out of the
  isolate.
- Workerd gave none back in 20 s. Cloudflare's docs say a cached isolate is reused "if it has not
  been evicted yet" and give no eviction rule ([Dynamic Workers](https://developers.cloudflare.com/dynamic-workers/getting-started/)).
- An agent that saves every minute for an hour passes experiment 93's 500 MB restart mark. That
  restart is already lossless and planned (12 to 17 a day today). Part 4 shows it is lossless for
  a reload too: a new workerd on the same data folder answered in 56 ms with `{count: 7}`, on v3,
  `count: 7`.
- So the lean is: let memory grow, and restart the local workerd on the existing mark. A watcher
  could also restart it after N saves. Either costs a person nothing they can see, since windows
  reconnect and catch up by rev ([T7](../docs/direction/a-local-first-sync-engine.md)).

## How others do it

Read on 2026-11-01. Every tool below swaps code by running the new code with state kept
somewhere the old code did not own, or by restarting and reading saved state back. None swaps
code under live memory without a rule about where the state is.

| Tool | What reloads | What is kept | When the shape changed |
|---|---|---|---|
| Erlang/OTP | one module, two versions at once | each process's state | `code_change/3` returns the new state; else a restart |
| Elm, elm-hot | the program | the old Model, fed to the new code | not checked; a view that throws says "please reload" |
| elm-watch | the program | the Model | it reloads the page and "tells you why" |
| React Fast Refresh | one component | its hooks' state | state resets; outside React, a full reload |
| Vite HMR | one module that `accept`s | what `dispose` puts in `hot.data` | no boundary: a full page reload |
| Phoenix LiveView | the page | nothing in memory; `mount` runs again | a full page reload |
| Durable Objects, deploy | the object | storage and hibernated sockets | storage is kept as it is; the code must read it |
| wrangler dev | all of workerd | storage on disk | the same |
| Electron | a page, or the whole app | the main process, for a page reload | the app restarts |
| VS Code | the extension host, or a window | terminals, in a pty host of their own | a restart |
| tmux | the config, by `source-file` | every session, in one server | not a code reload |

- **Erlang/OTP is the default answer.** "The code of a module can exist in two variants in a
  system: current and old" ([code loading](https://www.erlang.org/doc/system/code_loading.html)).
  A process moves to the new one on its next fully named call. A third load purges the old, and
  "any processes lingering in it are terminated". A `gen_server`'s `code_change/3` is "called by a
  gen_server process when it is to update its internal state during a release upgrade/downgrade"
  and returns `{ok, NewState}` ([gen_server](https://www.erlang.org/doc/apps/stdlib/gen_server.html)).
  A change to the runtime or its core libraries is `restart_new_emulator`, a whole restart
  ([release handling](https://www.erlang.org/doc/system/release_handling.html)), which also says
  "code is changed in as small steps as possible, and always kept backwards compatible".
- **Elm keeps the Model and swaps the rest.** elm-hot deletes the old program, evaluates the new
  one, and gives it the old model; it ignores `init`'s Cmds. It does not check the Model's type,
  and its source warns the first render "may fail if shape of model changed too much"
  ([elm-hot](https://github.com/klazuka/elm-hot), [hmr.js](https://raw.githubusercontent.com/klazuka/elm-hot/master/resources/hmr.js)).
  elm-watch: "Hot reloading is all about running new code with the previous state." It reloads the
  page when a record field is added, removed or renamed, "since model and functions aren't
  compatible", and "It also tells you why in the browser console"
  ([elm-watch](https://lydell.github.io/elm-watch/hot-reloading/)). Ours checks with the schema,
  so it does not need to guess from the record.
- **React and Vite keep state at a boundary, and fall back loudly.** Fast Refresh keeps function
  components' state and hooks, resets them when hook order changes, and does a full reload when a
  changed module is imported from outside React; `// @refresh reset` forces a reset
  ([Fast Refresh](https://reactnative.dev/docs/fast-refresh)). Vite (8.3.2 in our lockfile, via
  vitest only) swaps a module that calls `import.meta.hot.accept`, carries state in `hot.data`
  through `dispose`, and has `invalidate`; with no boundary, it reloads the page
  ([HMR API](https://vite.dev/guide/api-hmr), [hmr.ts](https://github.com/vitejs/vite/blob/main/packages/vite/src/node/server/hmr.ts)).
  The repo has no `@vitejs/plugin-react` and no React refresh runtime.
- **Phoenix reloads code per request and the page by WebSocket.** The code reloader runs on each
  request, "funneled through a sequential call operation"
  ([CodeReloader](https://phoenix.hexdocs.pm/Phoenix.CodeReloader.html)); live reload watches
  files and tells the page to reload, and swaps CSS without a refresh
  ([phoenix_live_reload](https://phoenix-live-reload.hexdocs.pm/readme.html)). A LiveView that
  reconnects runs `mount/3` again; on a full reload "all state will be discarded"
  ([LiveView](https://phoenix-live-view.hexdocs.pm/Phoenix.LiveView.html)). Its one queue for
  reloads is our queue.
- **Durable Objects keep storage, and since 2026-10-30 wait to swap.** "Durable Objects now defer
  code updates by default. When you deploy, an active Durable Object can keep running its current
  code for up to 5 minutes (300 seconds)"
  ([changelog](https://developers.cloudflare.com/changelog/post/2026-10-30-durable-objects-deferred-code-updates/)).
  An object still active at the end resets, and "Deferral is best effort"
  ([lifecycle](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/)).
  Memory is lost on reset; storage is not, and a code change "does not require a migration ...
  even for changes to how the code interacts with persistent storage"
  ([migrations](https://developers.cloudflare.com/durable-objects/reference/durable-object-class-migrations-legacy/)).
  "Connections accepted with the WebSocket Hibernation API remain connected when a Durable Object
  adopts new code after hibernating" ([WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)).
  Old and new code can run at once: "A request can reach the latest version of your Worker, which
  then calls a unique Durable Object running a previous version of your code"
  ([known issues](https://developers.cloudflare.com/durable-objects/platform/known-issues/)).
- **Worker Loader caches by id and promises nothing.** "If anything about the content changes, you
  must use a new ID", and "Two requests are never guaranteed to reach the same isolate"
  ([API](https://developers.cloudflare.com/dynamic-workers/api-reference/)). A content hash is the
  id, so this run's design follows the rule by construction.
- **Local workerd restarts on every bundle.** Miniflare's `setOptions` "restarts the `workerd`
  server" ([README](https://github.com/cloudflare/workers-sdk/blob/main/packages/miniflare/README.md)),
  and `wrangler dev` calls it on each new bundle
  ([LocalRuntimeController.ts](https://github.com/cloudflare/workers-sdk/blob/main/packages/wrangler/src/api/startDevWorker/LocalRuntimeController.ts)).
  Storage is kept across runs by default ([local data](https://developers.cloudflare.com/workers/local-development/local-data/)).
  Cloudflare's Vite plugin runs the Worker through Vite's module runner with HMR on
  ([cloudflare-environment.ts](https://github.com/cloudflare/workers-sdk/blob/main/packages/vite-plugin-cloudflare/src/cloudflare-environment.ts));
  whether a live object keeps its memory there was not read or tested.
- **Electron reloads a page or restarts the app.** `webContents.reload()` "Reloads the current web
  page" ([webContents](https://www.electronjs.org/docs/latest/api/web-contents)); electron-vite
  "Rebuilds and restarts the Electron app when main process files are modified"
  ([electron-vite](https://electron-vite.org/guide/hmr-and-hot-reloading)). Our lockfile has
  Electron 45.2.1 and no electron-vite.
- **VS Code keeps terminals outside what it restarts.** "Restart Extension Host" stops and starts
  the extension host ([source](https://github.com/microsoft/vscode/blob/937c6e91fd8cbc5b5e6a27128b3540415c98cccb/src/vs/workbench/services/extensions/electron-browser/nativeExtensionService.ts));
  since 1.88, "When an extension is updated, you can now restart extensions instead of having to
  reload the window" ([1.88](https://code.visualstudio.com/updates/v1_88)). On a window reload,
  terminals "reconnect to the previous process and restore its content"
  ([terminal](https://code.visualstudio.com/docs/terminal/advanced)), since the pty host is a
  process of its own ([source](https://github.com/microsoft/vscode/blob/937c6e91fd8cbc5b5e6a27128b3540415c98cccb/src/vs/platform/terminal/node/nodePtyHostStarter.ts)).
- **Zed reloads an extension in place, and the app on restart.** A dev extension's rebuild calls
  `reload` ([extension_host.rs](https://github.com/zed-industries/zed/blob/main/crates/extension_host/src/extension_host.rs));
  an update is applied "on restart" ([update](https://zed.dev/docs/update)).
- **tmux reloads config, not code.** It "loads configuration files once when the server process
  has started", and "The source-file command may be used to load a file later"
  ([tmux(1)](https://man.openbsd.org/tmux.1)). One server holds every session, so a client can
  come and go.

The pattern: what survives a reload is what lives outside the part that restarts. For us that is
already true. Facts live in the log, a process's own state lives in its object's storage, and
only a window's own model lives in memory
([the three homes](../docs/direction/a-local-first-sync-engine.md)).

## The design questions, with leans

Each lean is for `next/`, with why, cost and how sure. The note holds the same leans in its shape.

- **What reloads at each layer.**
  - A program in the brain: its processes swap at the next step, as above. 85%: measured here.
  - A window: the program's view module is swapped in the window, and the window machine's model
    is kept if the new view's schema decodes it; if not, that one tile reloads and rebuilds from
    the brain. Like Elm, not like a Vite server, since a browser tab on Cloudflare is a client too
    and has no dev server. 70%: no window was run here.
  - The core (libfabrika, the brain's own Worker): a workerd restart, Erlang's
    `restart_new_emulator`. Lossless, about 56 ms here and about 200 ms in experiment 93, since
    nothing lives only in memory. 80%.
  - Hands (Tier 4): a restart, with terminals in a pty process of their own, as VS Code. 60%:
    nothing built.
  - Electron's main process: a restart that does not stop the brain. 70%.
- **What state is kept.** The model, open terminals, jobs and a running lane all live outside what
  reloads, so all are kept. A refused process keeps running on its old code. 80%.
- **A new shape.** Migrate with the version's upcast, `code_change`. With no upcast, refuse and
  restart only that process, when the person says so. Never guess. 85%.
- **How a person learns code changed.** A quiet mark on that tile's title bar, a word and an icon
  (never color alone), gone at the next key. A refusal or an error stays until acted on, with
  `[Restart counter-1]`. An agent sees the same facts through its tools. 65%: no screen was built.
- **Where it is off.** A cloud stage never watches files: it takes a program's new hash by a
  deploy that a person said yes to. A live lane pins the build of its own stage programs for its
  life, while other programs, such as `runs`, still reload. 70%: the doubt is whether pinning
  surprises the person who just fixed a stage.
- **How it is tested.** Laws on Node against the program runner, with fixed seeds: no acked fact
  is lost; each Msg is stepped once; a reload to the same hash changes nothing; a fitting reload
  keeps the model equal; a refused one leaves that process on its old hash with one
  `code.refused`; bad code never runs; every step's build has an earlier `code.loaded`; only the
  saved program swaps. The race above is the test that would have caught the lost counter. 80%.
- **What the ledger must record now.** `build` on every step, Cmd and job record; `code.loaded`,
  `code.refused` and `code.failed` with program, hash, was, from, `by`, `at` and `said`; the
  window's build in its hello. Later, nobody can learn which code ran a step. 90%.

## What this cannot tell us

- **No window was reloaded.** The view half rests on Elm's and Vite's docs, not a run.
- **No hands, no terminal, no lane.** Tier 1 has no hands; the claims about them are reasoning.
- **A pure step only.** The test's versions return a model. A real tea program also returns Cmds
  and Subs; a swap that changes Subs must stop old Subs and start new ones, and that was not run.
- **Local only.** Nothing was deployed. Cloudflare's own Worker Loader eviction is undocumented,
  and the cloud claims come from its docs.
- **The rollback guess.** Rolling back on a throw and running the Msg once on the old code is safe
  only because the step is pure. A step that already sent Cmds is out of reach of this test.
- **One laptop, two runs.** The memory slope may differ with Effect out of the isolate (173 part 2
  says smaller) and on another machine.
- **The tracker ticket is for today's version and was not built.** Tracker #67, "Programs update
  live while agents edit them (host reload)", filed 2026-10-28 and still open, read on 2026-11-01.
  Its sketch: the host watches the files a repo's config read, waits 100 ms of quiet, loads them
  again with a `?gen=N` stamp, keeps state that fits its schema, keeps the old code and shows
  Restart when it does not, keeps the old code on a syntax error, and reports each reload as an
  event an agent sees. Its first step is the counter: "Edit it, see the tile change, count kept."
  Its open doubt is the bare-import trick on Node 24, at 70%. Every rule in it matches what this run
  found in `next/`'s brain; the difference is where the code loads (Node's module cache there,
  Worker Loader by hash here), which this run did not test for Node.

## How to run it

```sh
env -u TYPESAFE_API_KEY -u OPENAI_API_KEY -u CODEX_API_KEY nice -n 15 node experiments/183-hmr.ts
# RUNS=<n> race runs per mode (default 5), GENS=<n> saves (default 60); Miniflare in-process,
# data in a temp folder; nothing deployed, no network out; about 2 minutes; no model, $0
```

It finds esbuild in `experiments/173-worker-loader/`, so that package's dependencies must be
installed (`pnpm install` does it). The results are in `results/183-hmr.json`.
