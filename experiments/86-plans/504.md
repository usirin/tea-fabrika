# Plan: Layer patterns can't claim a file by its filename role, only by path prefix (#504)

Today a `--layers` path pattern can only be a path prefix, and `*` only works as a whole segment. A pattern like `**/*-plumbing.ts` matches nothing, so a repo that marks a module's role in its filename can't declare those roles as layers. After this change, `**` matches zero or more folders and `*` inside a segment matches part of a name (never crossing `/`), so filename-role layers claim their files at any depth. Plain prefixes work exactly as before, and when two patterns claim the same file, the more specific one wins or the gate refuses the tie with a clear message. The README documents both new forms.

Size: 4 stories, 1 task, 10 criteria, 1354 words.

## User stories

- **s1**: As someone running `code-graph . --layers --layer-rules <file>` on a repo whose module roles live in filenames (`*-plumbing.ts`, `*.service.ts`), I want to declare a layer as `**/*-plumbing.ts` and have every such file claimed, whatever folder it is in, so that so the layer gate, with its allowlist ratchet, unlayered census and per-site lines, enforces "business rules never import plumbing" and the rule doesn't have to fall back to an ast-grep check.
- **s2**: As someone whose existing `--layer-rules` file uses only prefixes and whole-segment `*`, I want their layers to classify every file exactly as they did before, so that so upgrading doesn't silently move files between layers and break their allowlist.
- **s3**: As someone writing a rules file that mixes directory-prefix layers and filename-role layers that can claim the same file, I want to know which layer wins, and to be stopped when two layers' patterns are equally specific, so that so a file's layer is never decided by an accident of pattern order.
- **s4**: As someone reading the README section "Declaring the stack (`--layer-rules`)", I want to see `**` and in-segment `*` documented next to `*`, along with how specificity treats them, so that so they can write role patterns without reading the source.

## Open questions

1. Should a tie between layers be refused when the rules file loads, from the patterns alone, or when a run actually finds a file that two tied patterns from different layers both claim?
   - Options: Refuse at load: any two patterns from different layers with equal specificity / Refuse at run time: only when one file is actually claimed by two tied patterns from different layers, naming the file / Don't refuse; keep a deterministic tiebreak such as declaration order
   - Lean: Refuse at run time.
   - Why: Whether two globs overlap can't be decided cheaply from the patterns, and a load-time rule would refuse harmless pairs: `services` and `packages` tie on depth, segments and characters (8 each) yet never claim the same file. The tie-refusal criterion and the README tie criterion depend on this.
2. When a directory-prefix layer (e.g. `services`) and a filename-role layer (e.g. `**/*-plumbing.ts`) both claim `services/billing/billing-plumbing.ts`, which should win?
   - Options: Keep the current order (depth, then whole literal segments) and only add literal characters as a final tiebreak; `**` adds no depth / Rank by literal characters first, so the role pattern usually wins over a short prefix / Always let a pattern that reaches the filename beat a prefix that only claims a folder
   - Lean: Keep the current order and add literal characters only as the last tiebreak.
   - Why: Ranking by characters first would reorder existing prefix-only configs: `services/*/src` (depth 3) currently beats `services/billing` (depth 2), but `services/billing` has more literal characters. That would break the 'prefix behaves as before' promise. The cost of this lean: a role layer can lose to a deeper directory prefix, which users must learn from the README. The specificity criteria and the README specificity criterion depend on this.

## Beside it: today's triaged criteria (8)

- A fixture repo declares three filename-role layers only — `plumbing` (`**/*-plumbing.ts`), `api-surface` (`**/*-api-surface.ts`), `business-rule` (`**/*-business-rule.ts`) — over at least three role files per layer spread across at least three top-level directories at depths from 1 to 5, including one upward import (a business-rule file importing a plumbing file, with plumbing declared below it) and several downward ones. `code-graph <fixture> --layers --layer-rules <file>` exits 1 and reports that upward edge at its real `file:line`, counts every edge between two role files as down, sideways or up (none of them `unlayered`), and after the upward import is added to `allowed` with its site count the same run exits 0. A test runs this end to end.
- `**` matches zero or more whole path segments: `**/*-x.ts` claims `a-x.ts` at the repo root (depth 1) and `a/b/c/d/e-x.ts` (depth 5), and `apps/**/y` claims both `apps/y` and `apps/p/q/y`. A test pins each case.
- A `*` inside a segment matches zero or more characters and never crosses `/`: `*-x.ts` claims `a-x.ts` and `-x.ts` but not `a/b-x.ts`; `pkg/*-x.ts` does not claim `pkg/a/b-x.ts`. A whole-segment `*` keeps its current one-or-more meaning. A test pins this.
- Every pattern that uses neither `**` nor an in-segment `*` classifies exactly as on `main`: the existing classification tests (`services` vs `services/*/src/domain`, `packages/core` never claiming `packages/core-contract`, `null` outside the lattice) pass unchanged, and a prefix pattern still claims its whole subtree.
- Specificity compares depth (segments other than `**`), then literal segments (segments with no `*`), then literal characters (characters other than `*` and `/`), higher wins. Tests pin that `apps/web/**/*-business-rule.ts` beats `**/*-business-rule.ts`, that `services` beats `**/*-plumbing.ts` on a file under `services/`, and that `**/billing-plumbing.ts` beats `**/*-plumbing.ts` on literal characters.
- When a file's highest-specificity matchers tie on all three keys and belong to different layers, `--layers` exits 2 with one line naming the file and both patterns, and reports no census or violations. Two tied patterns in the same layer, or tied patterns that never match a common file, are not refused. A test pins the refusal and both non-refusals.
- `packages/code-graph/README.md`'s "Declaring the stack (`--layer-rules`)" section documents `**` and in-segment `*` beside `*` with a filename-role example, states the three-key specificity order including the directory-beats-role consequence, states the tie refusal, and states that `?`, `[...]`, `{}` and `!` stay literal.
- A `minor` changeset for `@demlik/code-graph` naming the two new pattern forms and the tie refusal.
