# Plan: Layer patterns can't claim a file by its filename role, only by path prefix (#504)

Today a `--layer-rules` path pattern can only be a directory prefix, with `*` allowed only as a whole segment. `**` and a `*` inside a filename are read as literal text, so a layer like `**/*-plumbing.ts` claims nothing and every edge is counted unlayered. After the fix, `**` matches any number of folders (including none) and `*` inside a segment matches part of a name without crossing a `/`. Plain prefixes keep working as they do now. When patterns overlap, a pattern with more literal text wins, and a tie between two layers is refused instead of being settled silently by alphabetical order.

Size: 1 task, 13 criteria, 1240 words.

## Open questions

1. When a directory-prefix layer and a filename-role layer both claim a file, which one wins?
   - Options: Most literal characters wins (count only the non-wildcard text), with segment count as a later tie-break / Keep depth first, then literal characters (a deep directory prefix beats `**/*-role.ts`) / Any pattern with a filename part always beats a pure directory prefix
   - Lean: Most literal characters wins
   - Why: The ticket asks for this to be predictable but does not pick a winner, and users will notice the result. Counting literal characters ranks `apps/web/**/*-x.ts` above `**/*-x.ts` and does not punish `**` for being short. Keeping depth first would let almost any directory layer override a filename role. The two criteria about a directory layer and a role layer claiming the same file depend on this.
2. How is a specificity tie between different layers refused: only when the two patterns can actually claim the same file, or whenever their scores are equal?
   - Options: Refuse only when the tied patterns overlap (checked by analysing the patterns when the rules file is resolved) / Refuse at run time when a scanned file is actually matched by two tied patterns / Refuse any tie in score, overlapping or not
   - Lean: Refuse only when the tied patterns overlap, checked when the rules file is resolved
   - Why: Refusing every tie would break ordinary configs like `apps/api` and `apps/web` in different layers, which score the same but never collide. Checking when the file is resolved matches the ticket's 'at the schema boundary', but it needs an overlap test between two patterns. Refusing at run time is simpler, but whether it fires depends on which files exist. The two tie criteria depend on this.
