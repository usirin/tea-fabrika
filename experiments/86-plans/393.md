# Plan: code-graph --boundaries ignores imports from code outside every declared feature (#393)

`code-graph --boundaries` only checks an import when the importing file is inside a declared feature (B1/B2) or in a `lib` folder (B3). Every other file is skipped. So while a repo is adopting one feature at a time, most of its code can import a feature's internals and `--boundaries --ci` stays green. After this change, a new rule B4 flags any import from a file outside every declared feature and outside `lib` that reaches a feature anywhere other than its index.ts. B4 violations count toward the same per-scope ceiling in `boundary-ceilings.json`, so existing debt can be recorded and then ratcheted down.

Size: 3 stories, 1 task, 9 criteria, 1289 words.

## User stories

- **s1**: As a repo owner switching on `--boundaries` one feature at a time (e.g. Binclusive with only `access-gates` declared), I want code outside every declared feature that imports a feature's internals (anything but its index.ts) to be reported as a violation, so that declaring a feature actually walls it off on day one, not only against other declared features.
- **s2**: As a maintainer whose CI runs `code-graph . --boundaries --ci`, I want today's outside-to-internal imports counted under the same per-scope ceiling, recordable with `--write-ceilings` and failing on EXCEEDED or SLACK, so that existing debt can be frozen and paid down without blocking the switch-on, and new leaks fail the build.
- **s3**: As someone reading `--boundaries` output, its `--json` form, the README or the `--help` text, I want the new rule shown and documented as B4, next to B1–B3, so that they can tell why an edge was flagged and how to fix it (import through the feature's index.ts).

## Open questions

1. Should B4 count toward the existing per-scope ceiling by default, which can turn an already-recorded `--boundaries --ci` red on upgrade until someone re-runs `--write-ceilings`, or should it be opt-in?
   - Options: On by default, in the same per-scope count (as the ticket suggests); the changeset says to re-record / Opt-in through a boundary-rules key, so existing ceilings stay valid / Counted in a separate ceiling of its own
   - Lean: On by default, in the same count
   - Why: the ticket asks for the same ratchet, and closing the hole is the point. The cost is a one-time EXCEEDED in repos that already recorded ceilings (Binclusive wants this). The job criterion and the upgrade-note criterion depend on this choice
2. Which files count as 'outside' for B4: only files under src (including files directly in src, like its index.ts), or also files elsewhere in the scope (tests, scripts, scope-root config)?
   - Options: Every file in the scope that is not in a feature or lib, wherever it sits / Only files under src / Only files in a top-level folder under src (excluding files directly in src)
   - Lean: Every file in the scope that is not in a feature or lib
   - Why: the hole is about any non-feature code. Today's fixture already has a top-level src/index.ts reaching into a feature's store. Tests outside src that poke at internals would be flagged too, which some teams may not want. The job's fixture and its result depend on this choice
3. What kind name should B4 have in the `--json` output and the human report?
   - Options: outside-imports-feature / unowned-imports-feature / outside-feature
   - Lean: outside-imports-feature
   - Why: the kind is a published field of the JSON output, and it should read like B3's existing kind name. The render and JSON criteria depend on this name
