# Plan: code-graph --boundaries ignores imports from code outside every declared feature (#393)

Today `code-graph --boundaries` skips every import whose importer is outside all declared features and outside `lib`. So with one feature declared, the rest of the codebase can import that feature's internals and `--boundaries --ci` stays green. The current test suite even asserts this ("leaves a file outside every feature and lib unjudged"). After the fix, a new rule B4 reports any import from outside every feature into a feature file other than its `index.ts`, including its `rules/` folder. B4 counts toward the same per-scope ceiling, so existing debt can be frozen with `--write-ceilings` and ratcheted down. `lib` is already stricter than the ticket assumes: B3 forbids it from importing any feature, even through `index.ts`. That stays as it is, and `lib` gets no B4 exemption.

## Open questions

1. Should B4 also judge importers that are not under src/ at all, such as test/, e2e/ or scripts files in a scope, or only non-feature, non-lib files under src/?
   - Options: Judge every importer in the scope that is in no feature and not in lib, including files outside src/ / Judge only files under src/ (folders that are not features or lib, plus root-level src files)
   - Lean: Judge every importer in the scope. The ticket asks that nothing outside a feature reach its internals. Tests placed inside a feature folder are already 'inside', and existing debt can be frozen by the ceiling.
   - Why: Out-of-tree test and script files often reach into internals, so this choice can move ceiling counts a lot. It changes the fixture for the first criterion, and whether a test/ importer is counted in the ratchet criteria.
2. Should B4 count toward the existing per-scope boundary ceiling, which means repos that already recorded ceilings will see `--boundaries --ci` fail EXCEEDED after upgrading until they re-run --write-ceilings, or should it get a separate ceiling or an opt-in switch?
   - Options: Same ceiling; the release note tells adopters to re-record / Separate B4 ceiling per scope / Opt-in config flag, off by default
   - Lean: Same ceiling, with a changeset note. The ticket asks for this explicitly, and re-recording is the ratchet's normal path.
   - Why: This is a behaviour change users will notice in CI. The three ratchet criteria (record-then-pass, EXCEEDED, and the hint) assume the shared ceiling.
