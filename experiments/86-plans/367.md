# Plan: otel span-timing test fails under the full suite, passes alone (#367)

The span-timing test in the tea package fakes a clock that starts at 1000 ms and passes those numbers to OpenTelemetry as span start and end times. The OpenTelemetry trace SDK (sdk-trace-base 2.x) handles a plain number that is no larger than `performance.now()` as a time measured from process start, and shifts it to wall-clock time. So once the test worker has been up for more than about a second, which happens under the full `pnpm test` run, the root span no longer starts at [1, 0] and the start and end times can come from different time bases. Run alone, the worker is new and the numbers are read as epoch milliseconds. The fix: traced span times always mean exactly the milliseconds the run reported, however long the process has been up. Then the test passes the same way in the full suite and alone.

## Open questions

1. Should the fix go in the library (traceAgent and agentSpans always hand the SDK an unambiguous time), or only in the test (use epoch-sized clock values)?
   - Options: Library: convert each event time to an unambiguous time before giving it to the SDK, and add the small-clock test / Test only: start the fake clock at an epoch-sized value so it is never mistaken for process uptime
   - Lean: Library
   - Why: Any caller whose clock is not epoch milliseconds, such as a logical clock or a replayed run with small timestamps, would get silently shifted spans in production too. The test-only fix hides that. The second and third criteria only apply with the library fix. With a test-only fix, they would be dropped and only the first would stay.
