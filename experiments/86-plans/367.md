# Plan: otel span-timing test fails under the full suite, passes alone (#367)

The traceAgent span-timing test fails under the full `pnpm test` run but passes alone. The cause is not shared tracer state. Every test builds its own BasicTracerProvider. The test drives a fake clock that starts at 1000 ms, and traceAgent passes each event's `at` to OpenTelemetry as a plain millisecond number. The OpenTelemetry trace SDK reads a number no larger than the process's uptime as time since the process started, not as epoch time. A worker that has been up for less than a second sees the root span start at [1, 0]. A busy worker that has been up longer gets a start time shifted onto the wall clock. The same thing happens to any `@kamp-us/tea` user who runs an agent with a pinned or replayed clock. After the fix, the spans traceAgent and agentSpans export carry exactly the `at` of the transitions that opened and closed them, whatever the process uptime. The test is then deterministic under any load.

Size: 2 stories, 1 task, 4 criteria, 855 words.

## User stories

- **s1**: As a contributor or pipeline agent running the repo-root gates (`pnpm test`) or CI on an unrelated PR, I want the otel span-timing test to pass or fail the same way whether its file runs alone or in the full suite, so that so unrelated PRs don't go red and spend repair rounds on a test they never touched.
- **s2**: As a developer using `@kamp-us/tea`'s traceAgent or agentSpans with an injected clock (a pinned test clock or a replayed run), I want exported spans to start and end at exactly the `at` of the transitions that opened and closed them, so that so the trace shows the run's real timeline instead of times that depend on how long the process has been up.

## Open questions

1. Should this fix traceAgent and agentSpans themselves, or only make the test use epoch-scale clock values?
   - Options: Fix the library: pass `at` to OpenTelemetry in a form it can't misread, so users on pinned or replayed clocks get exact span times / Fix only the test: start the fake clock at an epoch-scale value (e.g. Date.UTC(2026, 0, 1)) and leave the library alone
   - Lean: Fix the library
   - Why: The flaky test is a symptom of a real library bug. Any `@kamp-us/tea` user who injects a small clock (tests, replay) gets span times that silently depend on process uptime. Fixing the test alone would hide that bug. The job criterion and the agentSpans small-`at` criterion depend on this lean. Under the test-only option, only the `pnpm test` criterion remains.

## Pointers (they bind nobody)

- `packages/tea/src/otel/otel.test.ts:207-217`: The failing test. The fake clock starts at 1000 (line 110), and the test asserts `root.startTime` equals [1, 0].
- `packages/tea/src/otel/index.ts:152-283, 339-377`: Each `startTime: at` and `span.end(at)` passes a bare ms number to OTel. Converting `at` to an HrTime tuple (or a Date) there avoids the SDK's guess that a number is relative to process start. Lines 280/283 call `end()` with no time on detach; leave those alone.
- `@opentelemetry/sdk-trace-base Span#_getTime`: The SDK rule behind the bug: a number input that is ≤ otperformance.now() becomes hrTime(inp + performanceOffset). HrTime and Date inputs skip this rule. Not vendored here (no node_modules in the snapshot), so check it in the installed version. A test can force the condition by stubbing performance.now to return a large value.
- `packages/tea/src/otel/otel.test.ts:83-89`: Shows each test builds its own provider and exporter, which rules out a shared global tracer provider.
- `.changeset/`: @kamp-us/tea is published, and fixing span times for users on an injected clock is a user-visible fix.
