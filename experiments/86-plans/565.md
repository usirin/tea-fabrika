# Plan: code-graph readAllowance refuses a driving adapter whose read decides nothing (#565)

Today `readAllowance` excuses B8 only when the driving file also imports, at runtime, a library of a `decidedBy` type. A thin read handler that decides nothing (it parses input, calls one listed driven read file and returns the answer) therefore stays B8 forever. After this change `decidedBy` can be left out of a scope's allowance. With it left out, any driving file that imports a listed read-only driven file is excused, and a listed file with a `write` data site still voids the allowance. A present `decidedBy` works exactly as today, an empty one is still refused with exit 2, and the README says that review holds "the adapter decides nothing".

Size: 3 stories, 1 task, 11 criteria, 1085 words.

## User stories

- **s1**: As a maintainer of a consumer repo with a hexagonal feature whose thin read handlers live in adapters/driving/, I want to declare a readAllowance for the feature's read-only driven files without naming a decidedBy library type, so that decision-free reads can stay in the feature's driving zone, without baselining each crossing or listing a meaningless library type.
- **s2**: As a repo that already declares readAllowance with decidedBy, I want its rules file to gate exactly as before, so that the new option is opt-in per scope and must not quietly loosen an existing gate.
- **s3**: As someone reading the code-graph README to set up a read allowance, I want the 'Read allowance (`readAllowance`)' section to explain both forms, and that review (not the tool) holds 'the adapter decides nothing' when decidedBy is left out, so that they can pick the right form and know what the tool no longer checks.

## Open questions

1. How does a scope opt out of the decidedBy proxy: by leaving the key out, or with an explicit marker such as "decidedBy": "none"?
   - Options: omit the key (the ticket's suggestion) / an explicit marker value / a separate boolean key
   - Lean: omit the key
   - Why: It is the smallest change, existing files keep gating unchanged, and an empty list is still refused, so a typo of [] cannot open the gate silently. The cost is that leaving the key out by accident widens the allowance, so the README must state that plainly. The job, the omitted-key criteria and the README criteria depend on this choice.
